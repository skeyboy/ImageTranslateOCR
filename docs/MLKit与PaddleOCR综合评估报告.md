# 执行摘要

本文对 Google ML Kit Text Recognition v2（以下简称 **ML Kit**）和 PaddleOCR 进行综合评估，重点覆盖移动端接入、OCR 质量上限、资源消耗、中国大陆可用性、行业定制、完整私有化以及长期维护成本。

> **综合结论：** ML Kit 更适合标准移动场景的快速上线与低维护运行；PaddleOCR 更适合复杂中文、行业定制、中国大陆交付和完整私有化。若产品同时面向 C 端体验与 B 端能力，建议采用统一结果协议下的双引擎架构。

两者并不存在一个在所有场景下绝对占优的结论：

- ML Kit 的核心价值是移动 SDK 工程成熟、实时体验稳定、开发和维护成本低。
- PaddleOCR 的核心价值是模型、训练、推理和部署链路自主可控，复杂场景质量上限更高。
- 中国大陆 Android 不应把依赖 Google Play Services 动态下载模型的 ML Kit unbundled 模式作为唯一方案。
- 正式决策前必须使用同一批真实业务图片进行端到端 A/B 测试；公开资料不能替代同口径验证。

# 1. 评估范围与边界

本报告比较的是 ML Kit 与 PaddleOCR 的文字检测、识别及端侧部署能力。

HY-MT 属于 OCR 后续的机器翻译模型，不参与 OCR 引擎优劣评分。完整图片翻译链路通常为：

```text
图片或相机帧
    ↓
文字检测、方向判断、文字识别
    ↓
ML Kit 或 PaddleOCR
    ↓
阅读顺序、文本框合并、语言判断、术语保护
    ↓
HY-MT 或其他翻译服务
    ↓
译文排版与图片回填
```

需要特别区分两个概念：

- **端侧运行**：图像识别在设备本地完成，原始图片不需要上传云端。
- **完整私有化**：模型权重、运行环境、版本、训练、日志和发布链路均由企业控制。

ML Kit 能很好地满足端侧运行和数据不出设备，但不能完全满足模型自主控制；PaddleOCR 可以覆盖完整私有化链路。

# 2. 综合能力对比

| 评估维度 | Google ML Kit | PaddleOCR | 综合判断 |
|---|---|---|---|
| 端侧接入 | Android/iOS 原生 SDK，接入快 | 需集成推理库、模型和原生封装 | ML Kit 优势明显 |
| 实时体验 | 标准相机与截图场景成熟 | 依模型、后端和设备调优而定 | 标准场景 ML Kit 更稳 |
| 复杂中文 | 普通印刷体稳定，模型侧优化空间有限 | 密集文本、票据、竖排和行业场景上限更高 | PaddleOCR 更适合深度优化 |
| 多语言 | 按 Latin、Chinese、Japanese、Korean、Devanagari 等脚本引入 | PP-OCRv6 提供统一多语种模型体系 | PaddleOCR 灵活性更强 |
| 训练定制 | 模型黑盒，不支持业务微调 | 支持检测、识别、字典和行业训练 | PaddleOCR 优势显著 |
| 版面能力 | 输出 block、line、element 等基础结构 | 可扩展版面、表格和文档解析 | 复杂文档选 PaddleOCR |
| 中国大陆 | bundled 可离线；unbundled 依赖 GMS | 不依赖 Google，可自有渠道分发 | PaddleOCR 风险更低 |
| 私有化 | 数据在端侧处理，但模型不可控 | 代码、模型、服务和训练均可自主管理 | PaddleOCR 更完整 |
| 维护成本 | 低，SDK 生命周期主要由 Google 管理 | 较高，需维护推理与模型版本矩阵 | ML Kit 更省工程资源 |
| 许可证 | 免费闭源 SDK，受 Google 相关条款约束 | Apache 2.0，商业使用相对清晰 | PaddleOCR 自主性更好 |

表中的“综合判断”属于工程选型判断，不代表厂商统一基准测试结果。当前公开资料没有提供 ML Kit 与 PP-OCR 在同一设备、同一数据集、同一输入分辨率和同一后处理条件下的直接成绩。

# 3. Google ML Kit 综合评定

## 3.1 主要优势

### 移动端工程成熟

ML Kit 对 Android CameraX、Android 图像对象以及 iOS 图像处理管线提供了直接支持。团队无需自行维护模型转换、移动推理框架和大量跨架构 C++ 代码，适合快速形成稳定产品。

### 实时与离线能力

OCR 在设备本地执行，能够处理相机视频帧和本地图片，并支持离线使用。这对即时翻译、隐私保护和弱网场景有直接价值。

### 标准场景投入产出比高

对于普通截图、菜单、路牌、名片和印刷文档，ML Kit 通常能以较低工程成本提供稳定结果。SDK 输出文本块、行、元素和坐标，足以支持基础图片翻译、文本框绘制和译文回填。

### Android 提供两种交付方式

- **Bundled**：模型静态打包进应用，首次使用无需下载，适合无网、无 GMS 或对确定性要求高的场景。
- **Unbundled**：模型由 Google Play Services 动态下载，可以减小初始安装包，但首次运行可能等待模型下载。

## 3.2 主要限制

### 模型不可训练

ML Kit 的 OCR 模型属于闭源黑盒。企业不能用自己的票据、工业字符或特殊字体数据微调模型，也不能自行修改字符字典和识别网络。

### 复杂场景优化空间有限

当竖排文字、弯曲文本、低清票据、特殊字体或工业字符出现系统性错误时，团队只能从拍摄质量、图像预处理和业务后处理方向改善，缺少模型侧优化抓手。

### 中国大陆和无 GMS 设备存在约束

Android unbundled 模式依赖 Google Play Services 下载模型，不适合作为中国大陆、无 GMS 设备、隔离网络或专用终端的唯一生产路径。此类场景应使用 bundled 模式，或保留 PaddleOCR 兜底。

### 多脚本增加包体

Google 官方当前说明：

- Android unbundled 模式每个脚本架构约增加 260 KB。
- Android bundled 模式每个脚本架构约增加 4 MB。
- iOS 每个脚本 SDK 对 App 大小的影响约为 38 MB。
- Latin 脚本在多数设备上可实现实时处理，其他脚本相对更慢。

实际包体应以目标 ABI、构建配置、商店拆包规则和最终安装结果为准。

## 3.3 定位结论

> ML Kit 是优秀的移动端隐私 OCR SDK，但不应被表述为完全自主可控的 OCR 私有化平台。

# 4. PaddleOCR 综合评定

## 4.1 主要优势

### OCR 链路完整

PaddleOCR 不只是一个识别 API。其能力覆盖文字检测、文字识别、方向判断、版面分析、表格识别和文档解析，可以从轻量端侧 OCR 扩展到复杂文档流水线。

### 支持行业训练与定制

企业可以调整检测模型、识别模型、字符字典和预后处理逻辑，也可以使用真实业务数据进行微调。这对票据、合同、工业字符、专有型号和特殊字体等场景非常关键。

### 部署自主性高

PaddleOCR 可以部署到：

- Android 等移动和边缘设备；
- 企业 CPU 或 GPU 服务器；
- 隔离内网和无外网环境；
- 浏览器及其他具有适配推理后端的平台。

模型可以随应用交付，也可以通过企业自己的模型服务或更新渠道下发，不依赖 Google 服务。

### 模型档位明确

当前 PP-OCRv6 提供 tiny、small、medium 三档模型，分别面向边缘、移动和服务器场景。企业可以在端侧和服务端使用不同档位，同时保持相近的数据接口和处理逻辑。

### 许可证清晰

PaddleOCR 项目采用 Apache License 2.0。与闭源 SDK 或带地域限制的模型社区许可证相比，其企业商业化、二次开发和私有部署路径相对清晰，但产品仍需保留必要的版权及许可证声明。

## 4.2 主要限制

### 端侧工程成本较高

端侧接入通常涉及：

- 推理库和模型格式；
- CPU 架构与 ABI；
- 算子和推理库版本兼容；
- 线程、内存、量化和硬件加速；
- Java、Kotlin、Swift 与 C++ 的边界封装；
- 模型下载、升级和回滚。

这些工作会明显增加初期开发成本和长期测试矩阵。

### 性能依赖调优

PaddleOCR 的最终速度和资源使用高度依赖模型版本、输入缩放、检测边长、CPU 核数、量化精度和设备推理后端。公开服务器指标不能直接代表目标手机上的实际效果。

### iOS 开箱体验较弱

与 ML Kit 相比，PaddleOCR 在 iOS 上通常需要更多推理工程和原生封装工作。若团队缺少 iOS/C++/模型部署经验，需要把这部分风险计入计划。

### 版本管理要求更高

生产环境需要同时锁定：

- OCR 模型版本；
- 推理库版本；
- 字符字典；
- 图像预处理参数；
- 文本框合并和阅读顺序算法；
- 量化和设备适配配置。

升级必须经过固定数据集回归，不能只替换模型文件后直接发布。

## 4.3 定位结论

> PaddleOCR 是一套 OCR 工程平台，而不是单一移动 SDK。其初期成本较高，但更适合复杂场景、行业定制和长期私有化。

# 5. 端侧性能与资源评估

## 5.1 不能直接比较公开速度

ML Kit 与 PaddleOCR 的公开性能说明使用了不同设备、模型、输入尺寸和测试方式，不能据此得出“某引擎快几倍”的结论。

至少需要固定以下变量：

- 相同原始图片和输入分辨率；
- 相同检测区域或检测边长；
- 是否启用方向分类、图像矫正和版面分析；
- 相同 CPU/GPU/NPU 使用策略；
- 相同线程数和预热条件；
- 相同文本框合并及过滤规则；
- 相同设备温度、电量和系统性能模式。

## 5.2 包体不能只看模型参数

ML Kit Android bundled 模型和 PaddleOCR tiny/small 模型都可能具有较小模型体积，但最终 App 增量还包括：

- 推理动态库；
- 多 ABI 原生库；
- 字符字典；
- 预处理和后处理代码；
- 多脚本模型；
- 商店拆包和压缩策略。

因此应以最终 APK、AAB、IPA 和设备安装体积为准，而不是仅比较参数量或单个模型文件大小。

## 5.3 连续屏幕翻译要测试稳定态

对于连续屏幕或相机翻译，单张图片延迟不足以反映真实体验。需要测试连续运行 10 至 20 分钟后的：

- P50/P95 帧处理延迟；
- 峰值内存与内存回收；
- 设备温升和 CPU 降频；
- 功耗和电量消耗；
- 丢帧、积压和界面卡顿；
- 文本框抖动、重复识别和译文闪烁。

# 6. 私有化部署评估

## 6.1 ML Kit：端侧隐私方案

ML Kit 的识别在设备本地完成，原始图片无需上传第三方服务器。这适合以下要求：

- 图片不离开用户设备；
- 弱网或无网情况下仍能识别；
- 低延迟实时处理；
- 团队不维护自己的 OCR 模型。

但是，企业无法获得和审计内部模型权重，无法自行训练，也不能将同一 ML Kit OCR 模型部署到私有服务器。因此，它更符合“数据不出设备”，而不是“完整模型私有化”。

## 6.2 PaddleOCR：完整私有化方案

PaddleOCR 可以将以下内容全部部署在企业或客户网络内：

- 模型文件和推理服务；
- 训练数据与训练环境；
- 推理日志、监控和审计；
- 模型仓库、灰度和回滚；
- 移动端、边缘端和服务器端运行环境。

企业还可以在端侧使用 tiny/small 模型，在服务器使用 medium 或文档解析模型，并利用业务数据持续训练。

> **私有化结论：** 如果采购或合规条款要求代码、模型、数据和日志全部位于客户网络内，并要求长期可维护，PaddleOCR 是更符合定义的方案。

# 7. 综合评分

以下评分为 1 至 10 分的相对工程判断，用于方案筛选，不代替业务验收。运维与升级成本一项的高分表示所需投入较低。

| 项目 | ML Kit | PaddleOCR | 说明 |
|---|:---:|:---:|---|
| 移动端接入效率 | 9 | 5 | ML Kit API 与移动平台集成更成熟 |
| 开箱实时体验 | 9 | 7 | PaddleOCR 结果更依赖模型和推理调优 |
| 复杂中文潜力 | 6 | 9 | 行业数据训练可提高 PaddleOCR 上限 |
| 行业定制能力 | 2 | 10 | ML Kit 不开放 OCR 模型训练 |
| 中国大陆部署 | 6 / 3[^mlkit-mode] | 9 | PaddleOCR 不依赖 GMS |
| 完整私有化 | 4 | 10 | 端侧运行不等于模型自主可控 |
| 长期自主可控 | 3 | 9 | PaddleOCR 可维护完整模型链路 |
| 运维与升级成本 | 9 | 5 | PaddleOCR 需要维护模型和推理版本矩阵 |

[^mlkit-mode]: ML Kit 在该项的 6 分对应 bundled 模式，3 分对应依赖 Google Play Services 的 unbundled 模式。

# 8. 业务决策矩阵

| 业务条件 | 建议方案 | 主要理由 |
|---|---|---|
| C 端移动应用，一期快速验证 | ML Kit bundled | 低集成成本、实时体验稳定、无需自建移动推理栈 |
| 国内 B 端、政企或隔离网络 | PaddleOCR | 不依赖 GMS，可完整私有化并锁定模型版本 |
| 票据、合同、工业字符、复杂版面 | PaddleOCR | 可训练、可扩展版面和表格解析，质量上限更高 |
| 普通截图、菜单、路牌、取景器翻译 | ML Kit | 标准自然场景的投入产出比更高 |
| 需要端云统一模型和审计 | PaddleOCR | 端侧、服务端、训练和监控链路均可控制 |
| 全球多市场快速分发 | ML Kit 或双引擎 | 降低端侧适配成本；中国大陆 Android 保留 PaddleOCR 兜底 |

# 9. 推荐架构

## 9.1 方案 A：C 端快速上线

```text
ML Kit bundled OCR
    ↓
端侧文本框合并与语言判断
    ↓
自建翻译服务
    ↓
端侧译文布局和回填
```

适合普通截图、菜单、路牌和相机即时翻译。图片可留在端侧，仅上传已识别文本。中国大陆 Android 应采用 bundled 模式，避免依赖 GMS 动态模型下载。

## 9.2 方案 B：企业完整私有化

```text
PaddleOCR small / medium
    ↓
版面分析、阅读顺序与段落恢复
    ↓
内网翻译服务
    ↓
结果审计、导出或译文回填
```

适合合同、票据、制造、物流、政企内网和行业定制。OCR、翻译、日志和模型管理均部署在客户网络内。

## 9.3 方案 C：双引擎长期架构

建议在业务层定义统一的 `OCRResult`：

```text
OCRResult
├── text              识别文字
├── confidence        置信度
├── quadrilateral     四点坐标
├── orientation       文字方向
├── language          语言或脚本
├── readingOrder      阅读顺序
└── engineMetadata    引擎和模型版本
```

平台层根据市场、设备和场景选择默认引擎，同时保留：

- 远程配置开关；
- 识别失败回退；
- 按机型和市场灰度；
- 质量样本回收；
- 引擎与模型版本记录；
- 相同后处理链路。

该架构能利用 ML Kit 的移动体验，同时在复杂或合规场景切换到 PaddleOCR，避免业务代码与某一个 OCR SDK 深度耦合。

# 10. 验证与验收方案

## 10.1 测试集

建议从真实业务中抽取 500 至 2,000 张图片，覆盖：

- 截图、相机、滚动页面和长图；
- 低清、倾斜、反光、模糊和遮挡；
- 深色、浅色、渐变和复杂纹理背景；
- 小字号、艺术字体和密集段落；
- 中文、英文、中英混排、日文和竖排；
- 票据、菜单、网页、聊天、合同和工业标签。

所有引擎必须使用相同原图、相同设备矩阵和相同文本框合并规则。

## 10.2 指标

### OCR 准确率

- 检测召回率和精确率；
- 字符错误率 CER；
- 词错误率 WER；
- 漏行率和重复行率；
- 阅读顺序准确率；
- 语言和脚本判断准确率。

### 端侧性能

- 冷启动时间；
- P50/P95 单帧延迟；
- 峰值内存；
- APK、AAB、IPA 和安装体积增量；
- 连续运行温升和耗电；
- 丢帧率和 UI 卡顿率。

### 产品质量

- 译文框错位率；
- 文本框抖动和重复闪烁率；
- 连续画面的稳定跟踪率；
- 用户纠错率；
- 图片翻译任务完成时间。

### 可靠性与合规

- 无网络、无 GMS、低内存和后台恢复；
- 横竖屏切换、长图和异常输入；
- 数据流、日志与崩溃上报范围；
- 模型来源和第三方 SDK 清单；
- 许可证和声明义务。

## 10.3 决策门槛建议

不建议只用单项 OCR 准确率决定结果。可以为业务设定加权总分：

| 指标类别 | 建议权重 |
|---|:---:|
| OCR 准确率与漏检 | 35% |
| 稳定态性能与功耗 | 25% |
| 产品视觉稳定性 | 15% |
| 工程维护成本 | 10% |
| 私有化与合规 | 10% |
| 包体与分发 | 5% |

若目标是政企或行业项目，应适当提高私有化、合规和复杂文本准确率的权重；若目标是消费级实时翻译，应提高性能、功耗和视觉稳定性的权重。

# 11. 风险清单

| 风险 | 影响 | 主要缓解措施 |
|---|---|---|
| ML Kit unbundled 模型无法下载 | 首次识别不可用 | 中国大陆和无 GMS 设备使用 bundled 或 PaddleOCR |
| ML Kit 特殊字符长期误识别 | 无法通过模型训练修复 | 增加业务纠错；复杂场景切换 PaddleOCR |
| PaddleOCR 推理库与模型不兼容 | 崩溃或识别异常 | 冻结版本矩阵，建立自动化设备回归 |
| PaddleOCR 多 ABI 导致包体增大 | 下载和安装转化下降 | App Bundle 拆分、按需模型下载、裁剪推理库 |
| 连续 OCR 导致发热降频 | 延迟上升和续航下降 | 帧节流、区域识别、缓存、动态降频和背压 |
| 双引擎结果结构不一致 | 业务代码复杂和回归风险 | 建立统一 `OCRResult` 及坐标、置信度规范 |
| 仅依赖公开指标做决策 | 线上质量与预期不符 | 使用真实业务数据进行同口径 A/B 验收 |

# 12. 最终结论

## 12.1 单一引擎选择

- 当前目标是尽快形成稳定的消费级移动体验：选择 **ML Kit**。
- 当前目标是复杂文档、国内企业交付、行业训练或完整私有化：选择 **PaddleOCR**。

## 12.2 长期产品选择

如果产品路线同时覆盖 C 端与 B 端，建议采用统一 OCR 结果协议下的双引擎架构：

- ML Kit 承担标准移动场景和低成本实时识别；
- PaddleOCR 承担复杂、离线、行业和完整私有化场景；
- 业务层保持文本框合并、翻译和渲染逻辑一致；
- 通过真实数据持续决定默认引擎和回退策略。

> 从长期能力建设看，PaddleOCR 的上限更高；从短期交付效率看，ML Kit 的投入产出比更高。最终决策应以同一业务数据集、同一设备和同一后处理链路的 A/B 结果为准。
