# 手机屏幕翻译：OCR 分段导致翻译断裂的解决方案调研

> **调研日期**：2026-08-04  
> **调研背景**：现有的 OCR+AI 翻译管线在处理手机截图（如 WhatsApp 消息）时，OCR 引擎按行切分文本导致句子被截断，逐段独立翻译后拼合结果语义断裂、质量极差。  
> **调研目标**：(1) 梳理业界对此问题的主流解决方案；(2) 研究翻译结果如何精确回贴到原图对应位置。

---

## 一、问题分析

### 1.1 问题本质

传统 OCR 引擎以「行」或「文本框」为检测单位，一段完整的自然段会被切成多个独立片段。每个片段独立送翻译引擎后，翻译引擎丧失上下文，拼合后出现语义断裂。

**对比示例**（WhatsApp 截图翻译）：

| 方式 | 效果 |
|:---|:---|
| OCR + 逐段翻译 | "适合该国，也不是web3的ommunity.then所有地狱都会松散。其余的是历史。" |
| 整段翻译 | "直到国家决定投资一些既不适合国家也不适合Web3社区的项目。然后，一切都乱套了。" |

### 1.2 根因

```
原文段落（连贯语义）
    ↓
OCR 按行检测，切成 5-6 个碎片
    ↓
每个碎片独立翻译（丧失上下文）
    ↓
拼合后语义断裂
```

核心问题出在 **OCR 输出粒度太细（行级）**，而翻译需要的最小语义单元是**完整的句子或段落**。

### 2.2 方案一：OCR 定位 + 文本框空间合并 + LLM 翻译（⭐ 推荐）

**这是目前业界公认的最佳实践**，核心思想是让 OCR 和 LLM 各取所长。

#### 核心原理

| 组件 | 擅长 | 不擅长 |
|:---|:---|:---|
| OCR 引擎 | 精确的文字定位（bounding box 坐标） | 理解段落边界、翻译质量 |
| VLM/LLM | 整段语义理解、高质量翻译 | 精确的像素级坐标定位 |

#### 管线架构

```
原始截图
    │
    ├──→ [OCR引擎] ──→ 逐行文本 + bounding box 坐标
    │                        │
    │                        ▼
    │               [文本框空间合并]
    │               按 Y 轴间距合并同段
    │               按标点规则辅助判断
    │                        │
    │                        ▼
    │           合并后的完整段落 + 段落级 bbox
    │                        │
    └──→ [VLM/LLM] ◄────────┘
              │
              ▼
        高质量段落翻译
              │
              ▼
     [渲染引擎] 将译文画到段落 bbox 位置
              │
              ▼
        翻译覆盖后的图片
```

#### 文本框合并逻辑

OCR 返回每一行的坐标 `(x, y, w, h)`，通过以下规则判断是否属于同一段落：

1. **Y 轴间距**：相邻两行的垂直间距 < 行高的 1.5 倍 → 同段
2. **X 轴对齐**：左边距一致或接近 → 同段
3. **标点辅助**：
   - 行尾无结束标点（句号/问号/感叹号）→ 下一行属同句
   - 行尾是逗号/连字符 → 肯定属同句
   - 下一行行首是小写字母 → 大概率是上一行续句

```python
def merge_text_blocks(ocr_results, line_gap_threshold=1.5):
    """根据 bounding box 坐标合并同段文本"""
    paragraphs = []
    current_para = {
        "lines": [ocr_results[0]],
        "bbox": list(ocr_results[0]["bbox"])
    }

    for i in range(1, len(ocr_results)):
        prev = ocr_results[i - 1]
        curr = ocr_results[i]
        
        # 计算行间距
        prev_bottom = prev["bbox"][1] + prev["bbox"][3]
        curr_top = curr["bbox"][1]
        line_height = prev["bbox"][3]
        gap = curr_top - prev_bottom
        
        if gap < line_height * line_gap_threshold:
            # 间距小于阈值，属于同一段
            current_para["lines"].append(curr)
            # 更新段落外接矩形
            current_para["bbox"][2] = max(current_para["bbox"][2], curr["bbox"][2])
            current_para["bbox"][3] = curr["bbox"][1] + curr["bbox"][3] - current_para["bbox"][1]
        else:
            # 新段落
            paragraphs.append(finalize_paragraph(current_para))
            current_para = {"lines": [curr], "bbox": list(curr["bbox"])}
    
    paragraphs.append(finalize_paragraph(current_para))
    return paragraphs

def finalize_paragraph(para):
    """将段落内的行文本合并为完整文本"""
    full_text = " ".join(line["text"].strip() for line in para["lines"])
    return {"text": full_text, "bbox": para["bbox"], "line_bboxes": [l["bbox"] for l in para["lines"]]}
```

### 2.3 方案二：VLM 直接看图翻译

**原理**：完全不走 OCR，直接把截图扔给 GPT-4o / Gemini / Claude 等视觉语言模型，让它"看图翻译"。

**优势**：
- 模型直接"看到"整段文字的视觉布局，天然理解段落边界
- 不存在分段问题
- 实现最简单

**致命缺陷**：
- VLM 的坐标定位能力很弱（没有像素→坐标的映射层）
- 无法精确返回每段文字的位置信息
- **翻译结果无法回贴到原图的对应位置**

**适用场景**：只需要知道"翻译成什么"而不需要覆盖显示的场景。

---

### 2.4 方案三：版面分析（Layout Analysis）先行

**原理**：在 OCR 之前，先用专门的版面分析模型把页面区域分成「段落」「标题」「表格」等语义区域，每个区域内的文字作为一个整体处理。

**推荐工具**：
- **PaddleOCR + PP-DocLayout**：开源，支持段落/标题/表格区域检测，有 bounding box 合并模式
- **LayoutParser**：学术界常用，基于 Detectron2
- **Google Document AI**：商用级，自动识别段落、表格、表单结构
- **Unstructured.io**：开源框架，擅长将文档转为结构化数据

**流程**：
```
原始图片 → 版面分析（检测段落区域） → 对每个段落区域做 OCR → 整段送翻译
```

---

### 2.5 方案四：OCR 后用 LLM 重组文本

**原理**：OCR 完成后，把所有碎片化的文本块扔给 LLM，让它重新组装成连贯段落，然后再翻译。

```python
raw_ocr_blocks = [
    "Web3行业尝试过，我们做得很",
    "好。国家决定投资没有的东西",
    "适合该国，也不是web3的",
    "ommunity.then所有地狱都会松散。其余",
    "的是历史。在那之后，"
]

prompt = f"""以下是 OCR 识别出的碎片化文本，请将它们重新组装成连贯的原文段落，
忽略错误的断行，保持原始语义：
{chr(10).join(raw_ocr_blocks)}"""

reconstructed = llm.generate(prompt)  # 先重组
translated = translate(reconstructed)  # 再翻译
```

**优势**：不需要修改 OCR 引擎，纯后处理  
**劣势**：多了一次 LLM 调用的成本和延迟；如果 OCR 切断位置恰好把单词也切断了（如 "community" → "ommunity"），重组效果受影响

### 2.6 方案五：端到端漫画翻译管线

漫画翻译领域已有非常成熟的完整管线，流程如下：

```
原图 → 文字检测(YOLO) → 语义分割(生成文字mask) → 涂掉原文(Inpainting) → OCR识别 → LLM翻译 → 排版渲染
```

## 三、翻译结果回贴到原图位置的技术细节

### 3.1 涂掉原文（Inpainting）

翻译后需要先擦除原文，再叠加译文。根据背景复杂度选择不同方案：

| 方法 | 适用场景 | 说明 |
|:---|:---|:---|
| **纯色填充** | 背景是纯色（如聊天气泡） | 直接用背景色填充 bbox 区域，简单高效 |
| **AI Inpainting** | 背景复杂（图片、花纹） | 使用 LaMa / AOT-GAN 等模型重建被文字覆盖的背景 |
| **模糊覆盖** | 不追求完美 | 高斯模糊原文区域后叠加半透明底色 + 译文 |

> **WhatsApp 场景**：聊天气泡背景是纯绿色/白色，直接纯色填充即可，不需要 AI inpainting。

### 3.2 自适应字号

译文和原文长度通常不同（中文往往比英文短），需要自动调整字号以适配原始 bbox 区域：

```python
def auto_fit_font_size(text, bbox_width, bbox_height, max_font=16, min_font=8):
    """自动缩放字号以适配给定区域"""
    for size in range(max_font, min_font, -1):
        lines_needed = estimate_lines(text, bbox_width, size)
        total_height = lines_needed * size * 1.4  # 行高系数
        if total_height <= bbox_height:
            return size
    return min_font
```

### 3.3 样式一致性

高级方案会提取原文的视觉风格以保持一致：

- **文字颜色**：从 bbox 内采样文字像素颜色
- **背景色**：从 bbox 周围采样背景色
- **字号推算**：根据原文行高推算
- **对齐方式**：根据原文 bbox 的 X 轴分布判断左对齐/居中

### 3.4 覆盖显示方式

| 方式 | 说明 | 适用场景 |
|:---|:---|:---|
| **浮动覆盖层** | 不修改原图，在上方叠加透明浮窗显示译文 | 实时屏幕翻译 |
| **原图修改** | 直接修改图片像素，擦除原文后写入译文 | 截图翻译后保存/分享 |
| **双语对照** | 原文保留，译文插入下方或侧边 | 阅读理解场景 |

## 四、推荐方案：面向 WhatsApp 截图翻译的混合管线

### 4.1 推荐架构

```
┌──────────────────────────────────────────────────────────┐
│                 WhatsApp 截图翻译管线                      │
│                                                          │
│  1. [OCR 检测]  →  获取每行文字 + bounding box 坐标       │
│        ↓                                                 │
│  2. [空间合并]  →  按 Y 轴间距合并为段落 + 段落级 bbox     │
│        ↓                                                 │
│  3. [LLM 翻译]  →  整段送 GPT / DeepSeek 翻译            │
│        ↓                                                 │
│  4. [渲染回贴]：                                          │
│     a. 用气泡背景色（绿色/白色）填充原文 bbox 区域         │
│     b. 自动计算字号以适配 bbox                             │
│     c. 在 bbox 区域内渲染中文译文                          │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 4.2 方案优势

- ✅ **翻译质量高**：整段翻译，不断句，效果与专业翻译软件一致
- ✅ **位置精确**：OCR bounding box 提供精确坐标
- ✅ **实现简单**：WhatsApp 气泡是纯色背景，擦除原文只需简单填色
- ✅ **成本可控**：OCR 成本低 + LLM 只翻译合并后的段落（调用次数少）

### 4.3 核心结论

> **不要在 OCR 和 VLM 之间二选一——让 OCR 做定位，让 LLM 做翻译，各取所长组成混合管线，是目前业界的最佳实践。**

## 七、PaddleOCR 专项分析：针对 WhatsApp 截图翻译场景

> **追加调研日期**：2026-08-04  
> **调研背景**：进一步分析 PaddleOCR 在本案例中的具体优势、处理流程和与其他 OCR 引擎的对比。

### 7.1 PaddleOCR 技术架构概览

PaddleOCR 是百度开源的 OCR 工具库，当前最新版本为 **PP-OCRv6**（2026年6月发布），采用三级模型体系：

| 模型层级 | 参数量 | 适用场景 | 检测 Hmean | 识别准确率 |
|:---|:---|:---|:---|:---|
| **Tiny** | 1.5M | 边缘/IoT 设备 | - | - |
| **Small** | 7.7M | 手机/桌面端 | - | - |
| **Medium** | 34.5M | 服务端高精度 | 86.2% | 83.2% |

核心技术栈：
- **文本检测**：DBNet（可微分二值化网络）+ RepLKFPN（轻量特征金字塔）
- **文本识别**：CRNN + EncoderWithLightSVTR（局部+全局注意力机制）
- **版面分析**：PP-DocLayout 系列（支持 23 种文档元素分类）
- **多语言**：单一模型覆盖 50 种语言（中英日 + 46 种拉丁语系）

### 7.2 PaddleOCR 处理 WhatsApp 截图的完整流程

针对你的具体案例（WhatsApp 英文消息截图翻译），PaddleOCR 的处理流程如下：

```
WhatsApp 截图
     │
     ▼
┌─── 第1层：PP-DocLayout 版面分析 ───┐
│                                    │
│  识别出：                          │
│  • 聊天气泡区域（text 类型）        │
│  • 用户名区域（title 类型）         │
│  • 时间戳区域（sidebar_text 类型）   │
│  • 头像/图标（figure 类型）         │
│  • 链接预览卡片（table 类型）       │
│                                    │
└────────────────────────────────────┘
     │
     ▼ 只处理 text 类型区域
┌─── 第2层：PP-OCRv6 文本检测+识别 ──┐
│                                    │
│  对每个聊天气泡区域内部：           │
│  • DBNet 检测每行文字 + bbox        │
│  • CRNN 识别每行文字内容            │
│                                    │
│  输出：                            │
│  [                                 │
│    {"text": "The Web3 industry     │
│     tried and we did",             │
│     "bbox": [72, 268, 388, 295],   │
│     "confidence": 0.97},           │
│    {"text": "quite well. Until     │
│     the country decided",          │
│     "bbox": [72, 298, 388, 325],   │
│     "confidence": 0.96},           │
│    ...                             │
│  ]                                 │
└────────────────────────────────────┘
     │
     ▼
┌─── 第3层：文本框空间合并 ──────────┐
│                                    │
│  根据 bbox 坐标 + 标点规则          │
│  将同一气泡内的多行合并为一段       │
│                                    │
└────────────────────────────────────┘
     │
     ▼
  整段送 LLM 翻译 → 渲染回贴
```

#### 关键差异：有版面分析 vs 无版面分析

| 步骤 | 无版面分析（你现在的方案） | 有 PaddleOCR 版面分析 |
|:---|:---|:---|
| 第1步 | 直接对整张截图做 OCR | 先识别出页面结构（气泡/用户名/时间戳） |
| 处理范围 | 截图上**所有文字**都会被识别（包括时间、用户名、状态栏） | 只处理**聊天气泡内的正文** |
| 分段依据 | 纯靠行间距猜测 | 版面分析已把每个气泡标记为独立区域 |
| 合并精度 | 可能把不同气泡的文字错误合并 | 不同气泡天然隔离，不会跨气泡合并 |

### 7.3 PaddleOCR 的核心优势（针对本案例）

#### 优势一：版面分析能力——从源头避免跨区域错误合并

**这是 PaddleOCR 最大的差异化优势。**

传统 OCR（如 Tesseract）只做"文字检测+识别"，不理解页面结构。当你有多个聊天气泡、用户名、时间戳、链接预览等元素混在一起时，简单的空间合并逻辑很容易出错：

```
❌ 无版面分析时可能出现的错误：

气泡1最后一行: "...come back for sure"          y=700
时间戳:         "22:43"                          y=720   ← 间距小，被错误合并
气泡2第一行:    "~ Lim CW  +65 9478 2794"        y=760   ← 也可能被合并

结果: "...come back for sure 22:43 ~ Lim CW +65 9478 2794"
翻译: "……一定会回来的 22:43 ~ 林CW +65 9478 2794"  ← 乱了
```

```
✅ 有 PP-DocLayout 版面分析后：

[聊天气泡区域1] → "The Web3 industry tried..." （完整段落，独立翻译）
[时间戳区域]    → "22:43"                      （不翻译，保留原样）
[用户名区域]    → "~ Lim CW"                   （不翻译，保留原样）
[聊天气泡区域2] → 下一条消息内容                 （独立翻译）
```

PP-DocLayout 支持 23 种文档元素分类，可以精确区分正文、标题、侧边栏文字、图片等，在 WhatsApp 截图场景下能正确识别：
- 聊天气泡 → `text`（需要翻译）
- 用户名 → `paragraph_title`（不翻译）
- 时间戳 → `sidebar_text`（不翻译）
- 链接预览 → `table` 或 `figure`（可选翻译）
- 状态栏 → 过滤掉

#### 优势二：文本检测精度业界领先

PaddleOCR 使用的 **DBNet**（可微分二值化网络）在"复杂背景文字检测"方面有显著优势：

| 场景特征 | Tesseract | EasyOCR | PaddleOCR |
|:---|:---|:---|:---|
| 纯色背景（聊天气泡） | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 密集文字排列 | ⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 混合字体/大小 | ⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ |
| 弯曲/倾斜文字 | ❌ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 多语言混排 | ⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| GPU 加速 | ❌ CPU only | ✅ | ✅ |

WhatsApp 截图的特点是：
- 文字密集（多行消息紧凑排列）
- 不同气泡间距很小（容易误合并）
- 可能包含 emoji、链接、电话号码等非标准文字

PaddleOCR 的 DBNet 在这些场景下表现最好，bbox 检测精度最高。

#### 优势三：`unclip_ratio` 等参数可精细调控

PaddleOCR 提供了细粒度的检测参数调整能力：

```python
from paddleocr import PaddleOCR

ocr = PaddleOCR(
    use_angle_cls=True,
    lang='en',
    
    # ===== 关键调参 =====
    det_db_unclip_ratio=1.2,    # 默认1.5，降低可防止行间错误合并
    det_db_box_thresh=0.5,      # 默认0.4，提高可过滤低置信度检测
    det_db_thresh=0.3,          # 二值化阈值
    det_limit_side_len=960,     # 确保高分辨率截图不被过度压缩
)

result = ocr.ocr('whatsapp_screenshot.png', cls=True)
```

| 参数 | 作用 | WhatsApp 场景建议 |
|:---|:---|:---|
| `det_db_unclip_ratio` | 控制检测框扩张程度 | **降到 1.0-1.3**，防止相邻行合并 |
| `det_db_box_thresh` | 过滤低置信度检测框 | **提到 0.5-0.6**，去除噪声检测 |
| `det_db_thresh` | 二值化严格程度 | 适当提高，让检测更"严格" |
| `det_limit_side_len` | 输入图片最大边长 | **设为 960+**，避免手机截图被压缩模糊 |

#### 优势四：支持移动端部署（Paddle Lite）

如果你的手机屏幕翻译需要在手机端本地运行（而不是上传服务器），PaddleOCR 提供了完整的移动端部署方案：

- **Paddle Lite**：轻量级推理引擎，支持 Android/iOS
- **PP-OCRv6 Tiny**：1.5M 参数，专为边缘设备优化
- 支持导出为 ONNX 格式，兼容更多推理框架
- 模型量化（INT8）进一步减小体积和加速

```
模型大小对比：
PP-OCRv6 Tiny:    ~3MB（适合手机端）
PP-OCRv6 Small:   ~15MB（手机端可接受）
PP-OCRv6 Medium:  ~70MB（建议服务端）
```

#### 优势五：Bounding Box 合并模式内置

PaddleOCR 的 PP-DocLayout 内置了三种 bbox 合并模式：

| 模式 | 行为 | 适用场景 |
|:---|:---|:---|
| `large` | 保留最大外框，删除包含在内的小框 | 整个气泡作为一个区域 |
| `small` | 保留最小内框，删除外围大框 | 精确到行级 |
| `union` | 保留所有框 | 需要自定义合并逻辑 |

对于 WhatsApp 场景，可以先用 `large` 模式让版面分析把每个气泡作为一个整体区域，再在区域内部用 `small` 模式获取每行的精确位置。

### 7.5 PaddleOCR 的局限性

客观来说，PaddleOCR 也有不足之处，需要注意：

| 局限 | 说明 | 缓解方式 |
|:---|:---|:---|
| **框架依赖** | 需要安装 PaddlePaddle 框架，比 pip install easyocr 复杂 | 使用 ONNX 导出后可摆脱框架依赖 |
| **段落合并非原生** | PP-OCRv6 本身不输出"段落"，需自写合并逻辑 | 结合 PP-DocLayout 的区域检测可大幅简化 |
| **WhatsApp 非标准文档** | PP-DocLayout 训练数据偏向正式文档，对聊天截图可能需要微调 | 可用 `unclip_ratio` 等参数调优，或在少量数据上 fine-tune |
| **Windows 部署偶有兼容问题** | PaddlePaddle 在 Windows 上的 GPU 配置比 Linux 复杂 | 推荐用 Docker 或 WSL2 |

### 7.6 结论与建议

#### 是否推荐在本案例中使用 PaddleOCR？

**✅ 推荐，PaddleOCR 是当前最适合本案例的 OCR 引擎。**

核心理由：

1. **版面分析能力解决了最棘手的问题**——区分不同聊天气泡、过滤时间戳/用户名，这是 Tesseract 和 EasyOCR 都没有的能力
2. **检测精度业界领先**——在密集文字、复杂背景等 WhatsApp 截图常见场景下，PaddleOCR 表现最优
3. **参数可调**——通过 `unclip_ratio` 等参数可以精确控制行间合并行为
4. **模型分层可选**——手机端用 Tiny（3MB），服务端用 Medium（70MB）
5. **支持移动端部署**——如果未来要做手机端本地翻译，Paddle Lite 是现成方案

#### 推荐的技术架构

```
手机截图
    │
    ▼
[PP-DocLayout-S]  版面分析（轻量模型，识别气泡/用户名/时间戳）
    │
    ├→ text 区域（聊天气泡）→ [PP-OCRv6-Small] 检测+识别 → 文本合并 → LLM翻译 → 渲染回贴
    ├→ title 区域（用户名）→ 保留原样（或可选翻译）
    ├→ sidebar_text（时间戳）→ 保留原样
    └→ figure（头像/图标）→ 跳过
```

这种"版面分析 → 区域级OCR → 段落合并 → LLM翻译"的四层架构，既解决了翻译质量问题（整段翻译），又解决了位置回贴问题（精确 bbox），还解决了跨区域错误合并的问题（版面分析天然隔离），是目前能找到的最优方案。

## 八、项目落地结论与验证记录（2026-08-05）

### 8.1 本项目主线结论

结合 `ImageTranslateOCR` 当前 Android 实现，主线不更换 OCR，而是在现有 OCR 和翻译 Provider 之间补齐稳定的「语义组」层：

```text
端侧 OCR（文字 + 行级坐标 + 屏幕尺寸）
    -> 端侧语义分组（角色、阅读顺序、组成员、组级外接框）
    -> 后端路由
       |- 本地模型：整组文本交给 ML Kit/实验模型
       |- Pnuts v1：保持 /api/v1/translate/regions 原协议兼容
       `- 自建 v2：上传 viewport + groups + regions + documentContext
    -> Qwen 结合全页上下文按 groupId 返回整组译文
    -> 端侧校验 request/session/generation/revision、组成员和坐标绑定
    -> 使用 Android StaticLayout 按真实设备字体完成字号、换行和组级回贴
```

这样保留端侧 OCR 的像素级定位优势，同时让翻译模型获得完整语义。服务端不重新推测或生成坐标，只回传经过绑定校验的原组坐标和排版提示，最终字体测量仍由端侧完成。相比由服务端直接返回字号和占用像素，这种边界可避免服务端字体与手机实际字体、缩放密度不一致。

### 8.2 已实现内容

1. `demo-server` 新增 Rust Axum 服务：`POST /api/v2/translate/groups` 和 `GET /healthz`。
2. 使用 Diesel Async + SQLite 保存请求审计元数据；不落库 OCR 原文和译文。
3. Qwen 使用本机 Ollama 的 OpenAI 兼容 Chat Completions API，当前质量优先默认模型为 `qwen3.5:9b`，`qwen3:4b` 保留为低资源回退；通过动态 JSON Schema 按 `groupId` 返回结构化结果，翻译文本不发送到线上 API 服务。
4. v2 请求包含屏幕尺寸、场景、翻译方向、全文上下文、语义组、原始 OCR 行、完整坐标、阅读顺序和修订号。
5. v2 响应包含组级译文、成员 ID、原组 `anchorBounds`、目标语言及 `layoutHint`。
6. Android 新增「自建服务」入口、基址和可选 Bearer Token 配置；本地、Pnuts、自建三种后端可独立切换。
7. 原 Pnuts v1 请求路径和数据格式不变。Pnuts 和端侧本地模型现在同样以语义组文本为翻译单位，结果再映射回组 ID。
8. 直播屏幕、一次截图和静态图片三条入口均已切换到「OCR -> 语义组 -> 整组翻译 -> 组级回贴」。

### 8.3 v2 交互约束

| 方向 | 关键字段 | 约束 |
|:---|:---|:---|
| Android -> 服务端 | `schemaVersion/requestId/sessionId/generation/translationRevision` | 用于协议版本、并发和旧响应隔离 |
| Android -> 服务端 | `viewport` | 所有 bbox 使用同一原始屏幕坐标空间 |

| Android -> 服务端 | `documentContext` | 提供全页语义与严格阅读顺序，最大 12000 字符 |
| 服务端 -> Android | `groupId/memberRegionIds/anchorBounds` | 必须和请求严格对应，否则端侧拒绝并本地回退 |
| 服务端 -> Android | `translatedText/targetLanguage` | 目标语言和内容需通过端侧脚本校验 |
| 服务端 -> Android | `layoutHint` | 仅给最大行数、最小缩放和溢出策略；最终像素排版由端侧决定 |

### 8.6 本地 Qwen 运行方式

本项目默认不使用 DashScope 等线上翻译 API。Axum 只连接同机 Ollama：

```text
Android -> http://Mac:8090/api/v2/translate/groups
        -> Axum 语义组服务
        -> http://127.0.0.1:11434/v1/chat/completions
        -> 本机 qwen3.5:9b（质量优先）
           或 qwen3:4b（低资源回退）
```

推荐配置：

```dotenv
QWEN_BASE_URL=http://127.0.0.1:11434/v1
QWEN_MODEL=qwen3.5:9b
QWEN_API_KEY=
QWEN_REASONING_EFFORT=none
QWEN_TIMEOUT_SECONDS=90
```

准备时先运行 `ollama serve`，再在另一个终端执行 `ollama pull qwen3.5:9b`。需要回退时设置 `QWEN_MODEL=qwen3:4b` 并重启 Axum，不改变 Android 接口。`/healthz` 会分别输出 `modelConfigured`、`modelReachable` 和 `modelAvailable`，只有后两项均为 `true` 才表示真实本地推理可以开始。本轮已在 24 GB Apple M4 上完成两个模型的下载和真实推理。

2. v2 响应必须沿用输入 `groupId`，服务能看到全文，却不能返回“把 5 个输入组合并成 1 个回贴组”的结构化决定，只能在每个旧组内补上下文，因而产生重复。
3. `TranslateManager` 已解析 `layoutHint`，但 `ImageTranslateActivity.TranslatedRegion` 未保留该字段。
4. 静态图片 `drawTexts` 使用 `group.unionBounds.height` 作为单行字号基线。5 行段落联合框高 139px，最小字号被错误设为约 95px，而真实单行高度约 18px，直接造成超大字号和裁切。

#### 推荐改造顺序

1. **P0：先修组级回贴。** 将 `layoutHint` 传入静态图片渲染；字号使用成员行高中位数，并按 `preferredMaxLines` 和 `minimumTextScale` 测量。裁切时禁止提交回贴。
2. **P0：增加内容区域和覆盖层过滤。** 排除设备窗口、状态栏、浏览器底栏及翻译控件；置信度只作辅助，因为设备 ID 的 OCR 置信度仍达到 0.851。
3. **P0：修复正文段落分组。** 联合归一化行距、左右边界和段间空白；本样本 8 个正文组应收敛为 4 个段落组。
4. **P1：给整页理解服务增加可选重分组表达。** v2 保持兼容，新增 `renderGroups/sourceGroupIds` 或 `groupingDecisions`，允许服务修正欠合并，同时保留 OCR region 几何追溯。
5. **P1：将 9B 整页耗时压到 8-12s。** 缩短提示词和 schema，限制输出 token，并验证 4B 快速首译、9B 质量回退或 MLX/llama.cpp 本地推理。

1. **源行数纠偏：** 对大面积 `BODY` 组，端侧最终 `maximumLines` 不得小于源 OCR 成员行数。服务 `preferredMaxLines` 只作为建议，不能把 17 行源组压成 6 行。
2. **有界紧凑排版：** 正常排版不满足时，字号比例逐步从约 `0.86` 降到 `0.72`，最低可在大面积文本上验证到 `0.68`；行距倍率从 `1.0` 降到 `0.90`、`0.86`，最低不建议低于 `0.82`。同时仅压缩组内上下内边距，不改变 OCR 锚点和外部区域。
3. **交互式溢出：** 达到最小字号和行距仍放不下时，图片内只写入可完整显示的前缀和尾部省略标记，结果页在区域尾部显示“更多”入口；点击后用弹框或底部面板显示完整原文与译文。

压缩和“更多”只应对大文本区域启用。建议初始门槛同时满足：

```text
role == BODY
memberRegionCount >= 4
sourceText.length >= 60
groupArea / viewportArea >= 0.03
groupWidth / viewportWidth >= 0.45
```

一两个单词、时间戳、手机号、品牌名、发送者、按钮和小标签必须排除，不能出现“更多”，也不能用过小字号强行翻译。

#### 展开方式约束

静态图片本身不能真正“向下展开”而不覆盖邻近像素，因此需要区分两个结果：

- **应用内结果页：** 可以在图片上显示尾部入口，点击后弹出完整译文；也可以用临时浮层展开，但关闭后恢复原图布局。
- **保存后的图片：** 不具备交互能力，只能保留缩略译文和省略提示。不能声称保存图仍可点击展开。

当前项目已有替换区域 marker、点击命中、原文/译文详情弹窗和 `ReplacementRegion` 数据结构，可以复用交互链路。需要补充的是：排版失败的译文目前不会进入 `replacementRegions`，后续应新增独立 `overflowRegions`，即使未完整回贴也要保留 `groupId`、原文、完整译文、bounds 和布局结果，供“更多”入口使用。

建议将 `drawTexts` 从只返回已回贴区域，改为返回明确的布局终态：

```text
FULL             正常字号完整回贴
COMPACT          有界字号/行距压缩后完整回贴
OVERFLOW_MORE    只回贴前缀，完整译文通过“更多”查看
PRESERVED        小区域或安全条件不满足，保留原文
```

#### 实施与验证顺序

“源行数纠偏、紧凑排版、更多弹框”都修改同一静态图片排版链路，可以放在同一批实现，但必须分层统计和验证：

1. 先只纠正 17 行组的 `maximumLines`，观察完整中文是否已能在原气泡内正常回贴。
2. 只有仍溢出的组才进入字体与行距压缩，记录最终字号比例和行距倍率。
3. 达到可读性下限仍失败时才生成 `OVERFLOW_MORE`，验证点击、关闭、缩放、marker 坐标和完整译文显示。
4. 回归短词、按钮、时间戳和手机号，确认均不会触发压缩或“更多”。
5. 保存最终图片，确认没有裁切、重叠或把交互浮层错误写入导出位图。

**方案结论：推荐实施。** 对当前 17 行聊天气泡，第一优先级不是继续缩字，而是取消错误的 6 行硬上限；在此基础上加入有限字号/行距压缩，并把“更多”作为大文本最终兜底。这样既能提高回贴成功率，也能继续保持现有“不裁切、不覆盖”的安全原则。

### 8.32 v3 回贴失败审计与原文覆盖几何（2026-08-08）

最新带实际回贴截图的 v3 记录证明，服务端权威分组和 Qwen 完整译文并不是原文漏出的主要原因。记录 `5894972e-720b-48c1-8fee-1cac58a613ed` 中，13 行正文、13 个成员 region 和两个 `FLOW_SLOTS` 均完整返回；端侧在译文提前用完首槽后把第二槽恢复为原图，导致末两行英文重新出现。记录 `57f262ee-5708-4d7c-bd9a-855611b41112` 则表明声明式文字替换仍使用保留纹理的模糊底图，造成英文从灰底中透出。
