## 根因

上一轮为避免单个物理不可用槽导致整组失败，形状排版器允许跳过不能容纳前缀的槽。新的候选搜索只判断“全文是否完成”，然后尽量放大字号。

在本例中：

1. 较大字号不能进入 68px 高的首槽；
2. 全部中文仍能放进下方 832px 高的大槽；
3. 排版器把“跳过首槽、在第二槽完整绘制”误判为更优方案；
4. 背景绘制仍覆盖全部服务端槽，导致首槽原文被擦除后留下空灰条。

这是端侧候选排序和部分槽安全恢复的问题，不需要修改服务端响应或重新翻译。

## 修复

- 先在最小允许字号计算基准候选；
- 如果基准候选能够使用首槽，则后续字号搜索必须保持从首槽开始，优先有限压缩而不是跳槽；
- 只有首槽在最小允许字号下仍物理不可用时，才允许跳到后续槽；
- 最终没有被文字段使用的槽恢复原图，禁止出现“已擦除但未绘制”的空白块；
- 保留原有 1px 不可用首槽用例，避免重新引入整组回贴失败。

## 结论

本次修复建立了明确优先级：阅读流连续性优先于追求最大字号；真正不可用的槽可以跳过，但不得留下被擦除的空白区域。重新采集同一页面时，箭头槽应显示“与此同时，”或该译文的首个可容纳前缀，下方大槽继续绘制剩余正文。
