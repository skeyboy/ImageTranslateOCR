# 无损压缩后 OCR 人工核验

本目录保存同一帧采集图的不同无损编码、PaddleOCR 原始响应和效率数据。

## 结论

- 建议 Android 在上传前编码为无损 WebP，服务端直接解码识别，不在服务端二次压缩。
- 无损 WebP 将图片从 374,809 B 降至 116,652 B，减少 68.9%；Base64 JSON 请求从 500,042 B 降至 155,830 B，减少 68.8%。
- 三种图片解码后的 RGBA 像素 SHA-256 都是 `67a0beb2d65008751b801efc3385ba56c8b50e26b186f6c2eb516b7069931e01`，差异像素为 0。
- 9 次 OCR 的文本、置信度、检测多边形和绘制框哈希完全相同，均识别 34 个区域，平均置信度为 0.952385。
- 无损压缩主要降低传输时间和流量，不会降低 PaddleOCR 的模型计算量。本机高负载下 OCR 耗时波动很大，没有观察到稳定的推理提速。

## 文件

- `capture-original.png`：原始验证帧，720 x 1600。
- `capture-optimized.png`：优化 PNG；本样本已是高压缩 PNG，因此文件体积没有进一步下降。
- `capture-lossless.webp`：无损 WebP，解码像素与原图完全相同。
- `capture-ocr-boxes.png`：带区域编号和绘制框的人工核验图。
- `ocr-recognition-data.json`：扁平化识别数据，包含文本、置信度、矩形框和多边形。
- `ocr-recognition-data.tsv`：适合表格查看的识别数据。
- `ocr-<编码>-r<轮次>.json`：PaddleOCR 每轮原始响应，共 9 份。

## 人工检查提示

区域 32 被 Android 悬浮窗遮挡，识别结果为 `Other car rental aiants sucn as eHi Car`。该结果在三种编码和全部轮次中一致，属于采集画面遮挡或 OCR 本身的问题，不是无损压缩导致。

当前 Android 网络引擎已优先使用 `Bitmap.CompressFormat.WEBP_LOSSLESS`，并保留超限回退路径。Android SDK 对该格式的定义是：`quality` 只控制压缩投入，不改变无损属性。

## Android 真机全链路复验

- 设备：`23113RKC6C`，Android API 36，局域网网关 `http://192.168.0.63:8090`。
- 原始设备画布：1440 x 3006；上传画布：766 x 1600；上传编码：无损 WebP。
- 结果：识别 2 个区域、翻译 2 个区域、失败 0 个区域，instrumentation 测试通过。
- 耗时：OCR 5,123 ms，翻译 7,239 ms，服务端总计 12,363 ms，客户端总计 12,567 ms，端侧编码、请求和响应解析等额外开销 204 ms。

这里的“无损”指 766 x 1600 上传画布编码、解码不改变像素。1440 x 3006 到 766 x 1600 的检测分辨率缩放是现有性能策略，本身不是源分辨率级无损；若要求保留原始采集分辨率，可取消缩放，但会增加传输和 OCR 计算量。
